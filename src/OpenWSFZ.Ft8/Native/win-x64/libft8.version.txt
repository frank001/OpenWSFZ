Built 2026-08-30 from branch qa/sup-b-2026-08-30, on top of the fix-negative-time-offset-
snr-collapse pin at shim 20260046 (SHA256 bc8efcf148046f199c057b62c7987c4b69f2dc62d72509

(dev-tasks/2026-08-30-sup-b-h12-instrumentation.md, implementing
qa/rr-study/2026-08-30-1149-architect-to-qa-spec-f001-sup-b-instrumented-suppression-
sizing.md Sec.3).

MEASURE-ONLY. Adds three new exported read-only getters --
ft8_get_h12_displaying_count(), ft8_get_h12_ambiguous_count(),
ft8_get_h12_divergent_count() -- counting how many EMITTED decodes resolved via the
12-bit nonstandard-callsign hash path, how many of those hit an ambiguous (>=2-entry)
probe chain, and how many of THOSE had their most-recently-announced match differ from
the first (displayed) one. Backs spec Sec.3.1's S = h12Ambiguous / h12Displaying and
D = h12Divergent / h12Displaying.

Mechanism: adds a uint32_t announce_stamp field to callsign_entry_t (sizeof
callsign_table_t: 64 KB -> 80 KB, .bss; not ABI-visible -- never marshalled to C#),
stamped in hash_table_add only (on both the genuinely-new-insert path and the
already-known re-announcement path), never in hash_table_lookup (TRAP 2 -- stamping on
lookup would contaminate announcement recency with lookup recency). A new, wholly
separate read-only function (hash_table_count_h12_multiplicity) replays
hash_table_lookup's own probe sequence purely to count matches and locate the
most-recently-announced one; it is never called from hash_table_lookup and never calls
it (TRAP 1). Per-message thread-local scratch, reset immediately before each message's
ftx_message_decode call and read only once that message is unconditionally headed for
results[] (the true emission point, not the decode-attempt point), so the three
counters denominate DISPLAYS, not decode attempts (TRAP 3).

hash_table_lookup's return value and the callsign it writes are byte-for-byte
unchanged. hash_table_add's existing reject-on-full and already-known no-op behaviour
is unchanged. No change to the 4096-slot capacity or eviction policy. No enablement of
any suppression/unique-match rule -- decode output after this change is identical to
before, plus three new process-lifetime counters and one new per-cycle log line
(h12Displaying/h12Ambiguous/h12Divergent).

=== fix-negative-time-offset-snr-collapse (FT8_SHIM_VERSION 20260046) ===

Built 2026-08-22 from branch fix/negative-time-offset-snr-collapse, on top of the
r2-coherent-llr-instrument Amendment 2/3 pin at shim 20260045 (SHA256
f0c081b968b04515f3fe76b853b423c77be1495d8e645115ceb3434f9e81fe58 win / 1ba510b8358029c36
e3ad9b8927bf80c140784655211f5e7bffddfb7eb7c046b linux, both still uncommitted at the time
this fix was drafted -- see this change's own tasks.md/notes for the two-commit plan that
lands both on this branch).

Corrects a defect in `ft8_decode_all`'s production `signal_db` loop (`ft8_shim.c`, the
loop immediately following each successful `ftx_message_decode`): for any candidate whose
`time_offset < 0` (an ordinary outcome of `ftx_find_candidates()`'s `-10..+19` search
range -- the signal's true sync position precedes the nominal 15 s decode window), the
per-block symbol index used to read `tones[]` was derived from `time_offset` CLAMPED to
a non-negative floor (`tones[b - b0]`) instead of the true, unclamped value -- silently
re-anchoring every one of the up to 79 averaged samples to the wrong tone bin and
under-reporting SNR by roughly 15-20 dB. Fix: `tone_col = tones[b - time_offset]`
(unclamped), with the loop's own upper bound `b1` narrowed to match (`time_offset +
FT8_NN`, clipped to `num_blocks`) so no symbol index can run past `FT8_NN - 1`. SNR
formula unchanged (`local_noise_floor - 26.5 dB`); pass count unchanged (2, pass-0 +
pass-1). Confirmed mechanically: `qa/rr-study/2026-08-22-1454-qa-to-architect-b-dt-c3-
results.md` (arm B-dt-C3) measured a 17.4 dB step in reported SNR co-located exactly with
the block at which `time_offset` turns negative. No ABI break, no struct layout change
(`FT8Result` stays 48 bytes), no new export.

  IMPLEMENTATION DEFECT FOUND AND FIXED DURING THIS CHANGE (recorded per HK-021/report
  discipline -- a real finding, not speculation): the refiner's initial implementation
  computed each Costas symbol's reference phase independently as
  `2*pi*ref_hz*absolute_sample_index/fs2`. This is WRONG for a continuous-phase FSK (CPFSK)
  signal -- it implicitly assumes each symbol's own tone had been running since sample 0,
  when the true transmitted phase at symbol j is offset by the ACCUMULATED phase of all
  preceding tones (data tones, for cross-block combining; the block's OWN preceding Costas
  tones, for within-block combining). Diagnosed empirically (REFINE_DEBUG env-var
  instrumentation, since removed): the correlation peak was smooth, sharp, and reproducible,
  but consistently mislocated by several samples/Hz on a CLEAN, NOISELESS synthetic signal at
  EXACT truth -- ruling out noise sensitivity. An independent Python re-implementation and an
  idealised hand-built CPFSK toy signal (bypassing downconvert_decimate, the Python synth, and
  GFSK shaping entirely) reproduced the identical mislocation, isolating the defect to the
  correlator's phase-reference model itself. Fixed by (1) combining the three Costas blocks
  non-coherently (magnitude-domain) across blocks, since inter-block data is unknown; (2)
  within each block, using a running phase accumulator that integrates the KNOWN 7-symbol
  Costas tone sequence continuously (matching qa/rr-study/synth/modulator.py's own
  cumsum-inclusive phase-integration convention), rather than seven independent per-symbol
  terms. Verified: the fix converges a clean synthetic signal's refined (df, dt) to
  (0.0000 Hz, 0.5 ms) -- the 0.5 ms residual is Stage C's discretisation grid, comfortably
  inside AC-1's 7.7 ms bar -- across four independent (freq, dt) test points. See
  native/ft8_lib_vendor/refine/sync_refiner.c's costas_coherent_sum() doc comment for the
  full derivation.
