  IMPLEMENTATION DEFECT FOUND AND FIXED DURING THIS CHANGE (recorded per HK-021/report
  discipline -- a real finding, not speculation): the refiner's initial implementation
  computed each Costas symbol's reference phase independently as
  `2*pi*ref_hz*absolute_sample_index/fs2`. This is WRONG for a continuous-phase FSK (CPFSK)
  signal -- it implicitly assumes each symbol's own tone had been running since sample 0,
  when the true transmitted phase at symbol j is offset by the ACCUMULATED phase of all
  preceding tones (data tones, for cross-block combining; the block's OWN preceding Costas
  tones, for within-block combining). Diagnosed empirically (REFINE_DEBUG env-var
  instrumentation, since removed): the correlation peak was smooth, sharp, and reproducible,
  but consistently mislocated by several samples/Hz on a CLEAN, NOISELESS synthetic signal at
  EXACT truth -- ruling out noise sensitivity. An independent Python re-implementation and an
  idealised hand-built CPFSK toy signal (bypassing downconvert_decimate, the Python synth, and
  GFSK shaping entirely) reproduced the identical mislocation, isolating the defect to the
  correlator's phase-reference model itself. Fixed by (1) combining the three Costas blocks
  non-coherently (magnitude-domain) across blocks, since inter-block data is unknown; (2)
  within each block, using a running phase accumulator that integrates the KNOWN 7-symbol
  Costas tone sequence continuously (matching qa/rr-study/synth/modulator.py's own
  cumsum-inclusive phase-integration convention), rather than seven independent per-symbol
  terms. Verified: the fix converges a clean synthetic signal's refined (df, dt) to
  (0.0000 Hz, 0.5 ms) -- the 0.5 ms residual is Stage C's discretisation grid, comfortably
  inside AC-1's 7.7 ms bar -- across four independent (freq, dt) test points. See
  native/ft8_lib_vendor/refine/sync_refiner.c's costas_coherent_sum() doc comment for the
  full derivation.

Shim version:     FT8_SHIM_VERSION = 20260038 (g2-hash-table-sizing-and-candidate-passband):
                  Item (a) — HASH_TABLE_SIZE 256 -> 4096. The callsign table keys on a 10-bit
                  bucket (1024 distinct values) placed on first probe at
                  (h10 * 23) % HASH_TABLE_SIZE; gcd(23, N) = 1 for every power of two, so that
                  placement is injective up to N = 1024 and the previous N = 256 collided 4:1
                  BY CONSTRUCTION, before the table was anywhere near full. Field symptom:
                  hashTableRejectCount = 35,379 on the 2026-08-08 20m leg against 595 across
                  C.1's entire 68-cycle corpus, with 5.5% of decodes carrying <...> against
                  the reference's 1.7%. sizeof(callsign_table_t) 4.0 KB -> 64 KB (.bss; the
                  DLL's on-disk size is unchanged at 55,808 bytes). Buys message TEXT only —
                  it CANNOT change the decode count, because message.c's two call sites already
                  discard a hashed callsign's resolution failure without affecting whether a
                  decode is produced. Session-scoped never-re-initialised lifetime (f-001
                  D1/D2/D3) and the absence of an eviction policy are deliberately UNCHANGED.
                  ONE version bump covers both item (a) and item (b): 20260034-20260037 are
                  unavailable (two claimed by unmerged branches, colliding; two are W2's
                  proposed renumbering targets) and 20260039-20260041 are RESERVED for the
                  R0/R1/R2 sync-refinement programme.
                  Previous: FT8_SHIM_VERSION = 20260033 (fix-d012-hash-table-add-overcounting):
                  hash_table_add's full-table guard previously ran before the "already known"
                  linear-probe check, so once the 256-slot table saturated, every subsequent
                  call incremented g_hash_table_reject_count and returned immediately —
                  including re-announcements of callsigns already resolvable in the table. A
                  real 9.5h corpus replay (42,429 total decodes) exposed a reject-count delta
                  of 73,627, an arithmetic impossibility. Fixed by reordering: the bounded
                  linear probe now always runs first; an already-known callsign is a no-op
                  regardless of table fullness; the count>=HASH_TABLE_SIZE reject-and-count
                  only fires after a full probe confirms the callsign is genuinely new. No
                  change to the 256-slot capacity or eviction policy; no ABI or struct layout
                  change; no new exported entry points.
                  Previous: FT8_SHIM_VERSION = 20260032 (f-005-hash-table-saturation-diagnostic):
                  observability-only follow-up to F-001's deferred saturation mitigation.
                  Adds one new exported read-only getter, ft8_get_hash_table_reject_count(),
                  returning the existing process-global g_hash_table_reject_count (the
                  reject-when-full counter added at 20260031 but not previously exposed). No
                  change to resolution behaviour, the 256-slot capacity, or the eviction
                  policy; struct layout unchanged (48 bytes). The only ABI change is the
                  single added export.
                  Previous: FT8_SHIM_VERSION = 20260031 (f-001-hashed-callsign-resolution):
                  ft8_decode_all's callsign hash table became a process-global session-scoped
                  static (g_session_hash_table) so a Type 4 nonstandard callsign resolves
                  across decode cycles; bounded at 256 entries (reject-when-full), AV-safe.
