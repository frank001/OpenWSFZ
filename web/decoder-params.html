Decoder parameters read-only

Every numeric parameter of the native FT8 decoder, read from the native library itself each time this page loads, not from app.json. The two can differ: the value shown is what the decoder is running with now. Reload the page to refresh it.

Runtime-settable values can be changed under Settings → Radio hardware → Advanced Decoder Settings; the suppression values have no setting here and stay at their defaults in the running application. Compile-time constants change only by rebuilding the native library.

Not included

A parameter table is only trustworthy if you can see what it leaves out. These numeric literals on the decoder's path are not in the table, and why. Protocol constants (the 6.25 Hz tone spacing, 79 / 174 / 91, the Costas pattern, 8 tones, 12 kHz) and structural values (array sizes, loop bounds, return codes) are not tuning values and are not listed. A numeric audit cannot see non-numeric decoder choices (the window function, the belief-propagation algorithm, the shape of the sync metric, the choice of max-over-tones soft demodulation): they are not parameters, so they appear nowhere on this page.

Derived values: none found. A literal equal to 6.25 Hz / K_FREQ_OSR (the 3.125 Hz sub-bin) or to symbol period / K_TIME_OSR (the half-symbol step) would be listed here as derived from that constant, never excluded as protocol; the audit found neither as a literal (both appear only in comments).

  • Waterfall dB quantisation: scale 0.5f and offset 120.0f (ft8_shim.c:1148, 1394, 1984), the exact inverse of the waterfall encoder 2·db + 240 with its 0–255 clamp (monitor.c:192) and the 1E-12f log floor (monitor.c:182). Not tabled: it is the waterfall's byte encoding, defined once by the encoder and inverted at three sites, so changing one without the others would corrupt the noise floor and SNR rather than tune anything. Doubt: it does fix the dB resolution (0.5 dB) and origin of everything downstream, including the noise floor the suppression writes back.
  • Callsign hash-table probe multiplier 23 (h10 * 23, ft8_shim.c:682, 711, 783). Not tabled: an implementation detail of the session callsign table, required to be identical at all three sites. Doubt: together with HASH_TABLE_SIZE (tabled) it decides which entries collide, so it can change which callsign a 12-bit hash resolves to when the table is crowded.
  • Ambiguity rule: two or more matching entries means not a unique match, so the 12-bit-hash callsign is suppressed (>= 2, ft8_shim.c:730, 859, 1912, 1925). Not tabled: the definition of "not unique" (F-001), not a threshold to move. Doubt: it decides whether such a callsign is displayed at all.
  • Sync-score neighbourhood: one frequency bin either side and one time block either side of each Costas symbol (decode.c:223, 229, 238). Not tabled: the shape of the sync metric, not a scalar threshold. Doubt: a decode-sensitive design choice; the cut-off applied to the score, K_MIN_SCORE, is tabled.
  • Waterfall front-end scaling: FFT normalisation 2.0f / nfft (monitor.c:75). Outside the files the audit rule names (patched/common/monitor.c is not a patched/ft8/*.c file), listed rather than omitted. Not tabled: a signal-processing definition of the waterfall.
  • Belief-propagation tanh/atanh approximation: the clamp at ±4.97 and the rational-approximation coefficients (native/ft8_lib_vendor/ft8/ldpc.c:223–249). An unpatched vendored file, outside the files the audit rule names; listed rather than omitted. Not tabled: a numerical approximation, not a tuning knob. Doubt: the clamp point affects belief-propagation output.
  • Noise-floor median (the percentile): the 2 in cum * 2 >= total, which selects the 50th percentile of the waterfall histogram, at ft8_shim.c:1146 (the global noise floor) and :1392 (the local noise floor). Not tabled: hoisting it would need a native rebuild and a new library, for a value that nothing in this change makes settable and no stage sweeps. Both sites must carry the same percentile; a divergence between the global and the local estimator would be a defect, not a tuning option. Doubt: the 2 is a percentile selector, a free choice and not protocol (cum * 4 would be the 25th percentile). It sets noise_raw, the value the suppression writes back, and the SNR input to the suppression ramp (the snr it is fed). A median rises with band occupancy, so in exactly the dense scenes this arm targets, the estimator is pulled toward the signals it is meant to exclude. (Using the median as the estimator at all is a non-numeric choice and is the same doubt, not a second one.) This is not a finding that the 50th percentile is wrong, and it arms no sweep: if a later stage wants the percentile swept, it is hoisted and tabled in that arm, with its own rebuild and the Captain's go.
