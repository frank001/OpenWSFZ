## 1. The rule (one sentence)
**A late decode (batch 2 or 3) counts as heard. It may cause any message-driven transition a batch 1 decode causes. It never counts as a cycle. Its reply goes in the next own-parity slot that can still start within 2.36 s.** (2.36 s = 15 s - 12.64 s, the latest start for a whole FT8 signal.)

## 2. What to build (numbers match the design; D = design section)
1. **`DecodeBatch` gets `int BatchNumber = 1`** (D1). Every existing constructor call stays valid. `DecodePump.PublishFirstAsync` writes batch 1; **`PublishSecondAsync` is used for batch 2 AND batch 3 on both flag-ON paths** (the residual-only two-stage path and the Deep staged path) and now also writes the answerer and caller channels, with the right `BatchNumber`, beside the external-reporting write it already does. The cycle-audio archive stays as it is (D5, out of scope: one enqueue per window at batch 1).
2. **Channel capacity 2 -> 8** for the answerer and caller channels only (`Program.cs` ~l.345 and ~l.351; `DropOldest` kept; the external-reporting channel and the framer channels are not touched). The 8 is the Architect's judgement (3 batches x 2 cycles + 2 spare, HK-038); AC8 tests it.
3. **Only a batch 1 is a cycle** (D1). A supplementary batch (number 2 or 3) must not: increment or reset retry / no-response counts, call `RetryOrAbortAsync`, consume `_skipNextRetry`, count CQ repeats (caller), fire an operator-armed pending target or jump-in, or reset the watchdog by itself (D2 table). It MAY cause: a forward transition on a matching message (report, R-report, RR73/RRR, an answer to our CQ, auto-answer of a CQ), and the abort when the partner is working another station.
4. **Two guards** (D2), both logged with the batch number and the reason: **stale** (a batch 2/3 of cycle N is ignored if a batch 1 of a LATER cycle has already been processed) and **already answered** (ignored if batch 1 of N already caused a message-driven transition).
5. **Timing of the reply** (D3 + Amendment 1). Let *t* = the time the **service processes** the batch (its time provider's now, NOT the decode-completion time; R3), *S* = cycle N's start + 15 s.
   - **Immediate:** no transmission running, the reply's parity is *S*'s, and *t* <= *S* + 2.36 s => transmit now, exactly as batch 1 would, untruncated.
   - **Otherwise deferred.** *Wait states:* make the state transition NOW (partner, reports, next message in `_lastTxMessage`, retry count reset to 0) and hold the reply as a **deferred transmission**. *Idle late-CQ auto-answer ONLY (R2):* make **NO state change until the answer is actually sent**; the broadcast/UI state stays Idle while it is deferred; a drop leaves Idle untouched.
   - The deferred transmission is sent on the **first later batch 1 whose next cycle has the reply's parity** (in practice batch 1 of N+2 sends it in N+3). **Before sending, that batch 1 runs through the NEW state's handler first.** The deferred TX is **superseded only if that handler would make a message-driven transition** (forward, or the partner-busy abort). **Anything else sends it, including a repeat of the message that caused the late transition (R1).** Sending it is **not a retry**: no retry increment, then `_skipNextRetry = true` as after any transmission. A batch 1 of the wrong parity (our own slot N+1) is not a missed response while a transmission is deferred.
   - A deferred **late-CQ answer is dropped** if an intervening batch shows the CQ station sending to someone else (destination neither CQ nor us), and also if an **operator-armed pending target or jump-in fires first** (the operator wins).
   - A newer message-driven transition supersedes a deferred transmission; the watchdog resets when the deferred TX is sent.
6. **Answerer snapshot merged per cycle** (D4): `_lastIdleDecodeBatch` holds one cycle. A batch 2/3 with the **same** `CycleStart` **appends** its results; a batch 1 of a **newer** cycle **replaces**; a batch 2/3 of an **older** cycle is dropped. `TryEngageExternal` then accepts a reply to a pass-0 station and to a residual/third-pass station. The caller has no snapshot.
7. **Logging (AC10):** every batch-2/3 decision in both services logs the batch number and one outcome from {`applied-immediate`, `applied-deferred`, `superseded`, `ignored-stale`, `ignored-answered`, `no-match`}, in the existing log style, **aggregates only: no message text, no callsigns** (HK-037/NFR-021). QA will count these lines over an endurance run; use exactly these tokens.
8. **Both services**, same structure: answerer (`QsoAnswererService.cs`) and caller (`QsoCallerService.cs`); the router that activates one service at a time stays as it is.
🛑 **Out of scope:** holding a batch-1 retry to wait for batch 2; answering in any slot other than through item 5; any decoder change; the decode-panel display (already shows batches 2/3); the archive "NoDecodes" effect for batch-2/3-only cycles (the Captain's housekeeping; do not fix, but mention it in the hand-back if your tests touch it). If the existing code makes any rule above impossible without a larger change: **STOP AND REPORT**, do not improvise a variant.

## 3. Tests (mechanical; fake time provider and fake PTT; synthetic callsigns only, `Q`-prefix, NFR-021). Names in the hand-back must map to AC numbers.
- **AC1:** with no supplementary batches today's behaviour is unchanged. Every existing answerer, caller and pump test passes **unchanged** (list any you had to touch and why: expected none). **Integration replay (R4):** a scripted fake decode source feeds **batch 1 only** and includes CQs, answers, reports, RR73 and **at least one missed-reply retry**; run it on `0c7124db` (a throwaway worktree, not this branch) and on the new tip; compare the transmitted message sequence and slot starts as **exact lists**. A **second run of the script feeds EMPTY batches 2/3** and must give the same lists.
- **AC2:** for each service x each Wait state: a batch 2/3 with no match leaves the retry count, `_skipNextRetry`, the CQ-repeat count and the watchdog unchanged and transmits nothing.
- **AC3 (deferred reply):** batch 1 of N no match => retry in N+1; then batch 2 of N with the partner's message => state advances; no transmission in the remainder of N+1 or in N+2; the reply is transmitted starting at N+3's slot; the retry count is 0 after it and sending it does not increment the count.
- **AC4:** batch 2 of N matching, no TX running, *t* <= *S* + 2.36 s on the right parity => transmitted in slot *S*, untruncated; at *t* = *S* + 2.37 s => deferred per AC3. (Boundary pair, both sides.)
- **AC5 (supersede):** while a reply is deferred, a batch 1 of N+2 carrying a message that causes a different transition => that transition wins and the deferred message is never transmitted.
- **AC6 (late CQ):** auto-answer on, CQ only in batch 2 => answered by the AC3/AC4 timing; service state and broadcast state stay Idle until the answer is sent; an intervening batch showing the CQ station sending to another station => answer dropped, service still Idle (untouched); an operator pending target / jump-in firing first => dropped.
- **AC7:** the partner sending to another station in a batch 2/3 aborts exactly as from batch 1.
- **AC8:** a batch 2 of N read after batch 1 of N+1 is ignored (logged `ignored-stale`); a batch 2 of N after batch 1 of N caused a transition is ignored (logged `ignored-answered`). **Channel test:** 3 batches per cycle for 4 cycles with a 12.64 s blocking transmission in each own slot => **no batch 1 is dropped** (state the assertion on the capacity, not only on the outcome).
- **AC9:** batch 1 then batch 2 of the same cycle => `TryEngageExternal` accepts a reply to a batch-1 station and to a batch-2 station; a batch 2 of an OLDER cycle does not change the snapshot.
- **AC10:** every decision path above logs the batch number and exactly one outcome token (assert on the log capture, one test per token).
- **AC11 (R1):** a late transition on the partner's report, the partner repeats the **identical** report in N+2 => exactly **one** transmission, in N+3, and the retry count is 0 afterwards.
- **Pump:** `PublishSecondAsync` writes the answerer, caller and external channels with `BatchNumber` 2 / 3; batch 1 still writes all three with 1; the archive is enqueued once per window.
- The unfiltered `dotnet test --nologo` passes on Windows and WSL (quote the exact command and totals; a filtered-out suite is not green, HK-022). Do not loosen an existing assertion.
- **Flake rules (TESTING_STRATEGY.md section 11):** wait on a positive condition (`OpenWSFZ.TestSupport.Poll.*`), never a fixed delay; "queue empty" is not "processed" (use the fake time provider and `ObservedDecodeChannel` where the QSO service tests already do); no no-op delay seam plus exact-count assertion racing a background loop.

## 6. What the Captain should expect (so nobody is surprised)
On sol-class timing a batch 2 is processed about 4 s into the slot (batch 1 at about *S*+1 s, plus the residual pass median of 3.0 s), already past the 2.36 s guard, so **most late replies are deferred one full round (sent in N+3)**; on a faster PC the immediate path will sometimes apply (how often is not measured). That is ordinary FT8 practice (a reply one round late), not a defect.
