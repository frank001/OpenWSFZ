## Two code facts that shape the design (Architect, K1/K2)
- **K1:** `message.c` l.837-838 saves EVERY standard callsign it unpacks into the hash table. A 0.1 decode therefore saves its two hounds, and a FALSE 0.1 decode would save two random calls for the rest of the session.
- **K2:** the shim's table (`ft8_shim.c` l.652-675) is session-scoped, never cleared, never evicts: up to 4,096 entries over 1,024 ten-bit buckets.

## 1. The native unpacker (`native/ft8_lib_vendor/ft8/message.c`, `ftx_message_decode`)
1. Handle `FTX_MESSAGE_TYPE_DXPEDITION` (i3 = 0, n3 = 1) in the `switch` at `message.c:308` (today `default:` returns `FTX_MESSAGE_RC_ERROR_TYPE`). Layout (`message.h:42`): **28 + 28 + 10 + 5 = 71 payload bits** = `c28` (callsign 1) | `c28` (callsign 2) | `h10` (10-bit hash of callsign 3, the Fox) | `r5` (report), then n3 and i3.
2. **Rendered text:** `<call1> RR73; <call2> <<call3>> <report>`, e.g. `Q1ABC RR73; Q2XYZ <Q3DX> -12`. `call1`/`call2` come from the existing 28-bit unpack exactly as the standard path renders them. `call3` is rendered through the hash interface by its 10-bit hash (`FTX_CALLSIGN_HASH_10_BITS`, `message.h:60`): resolved => `<CALL>`, unresolved => `<...>`. **Report `r5` (C5):** the protocol paper gives -30 to +32 dB in 2 dB steps (32 values for 5 bits); derive the exact formula from the paper, cite the section in the hand-back, render it as a signed two-digit number (`-12`, `+03`). QA checks every matched report against WSJT-X's own text (any mismatch is a formula error and a STOP).
3. 🔴 **Memory safety and the length bound (C1) - the hard requirement.** The public result field is `message[36]` (max **35** characters; `ft8_shim.h:816`, `Ft8NativeResult.cs:35`, `FTX_MAX_MESSAGE_LENGTH`), and `message.c` uses a fixed `char buf[35]` split into 14/14/6-character fields. **Do not change the ABI struct** (phase 3 decides whether it needs the raw `h10`, and any ABI change can then widen the text field in the same change). Lengths in characters (`RR73;` with its two spaces = 7, report = 3, brackets included):

   | call1 | call2 | call3 | length | fits in 35? |
   |---|---|---|---|---|
   | standard (up to 6) | standard (up to 6) | resolved (up to 13) | 6+7+6+1+13+1+3 = **37** | **no** |
   | standard (up to 6) | standard (up to 6) | `<...>` (5) | 29 | yes |
   | a resolved 22-bit hash in the c28 field (up to 13) | standard (6) | `<...>` | 13+7+6+1+5+1+3 = **36** | **no** |
   | `<...>` | `<...>` | `<...>` | 27 | yes (the floor) |

   **Fixed degradation order, applied until the text fits in 35:** (1) render `call3` as `<...>`; (2) if it still does not fit, render any hashed `call1`/`call2` as `<...>`, **`call2` first**. The 27-character floor then proves it always fits (the special tokens, up to 7 characters, fit at the floor too: 31). Keep an error return only as a defensive `assert` that is **never taken**. No write past any buffer, ever; the output is always NUL-terminated. **Exhaustive test:** decode every value of `h10` and `r5` and a spread of `c28` values (all special tokens and the whole hash-form range), assert the length bound, the terminator and that the assert branch is never reached; put the table above in the test's comment. Run it under **AddressSanitizer on the WSL leg** (say which tool you used).
4. Keep the vendored file's licence header; mark the added code as OpenWSFZ's (MIT-compatible, your own implementation). Update the third-party notes if the repo keeps a per-file modification record for the vendored library (check what earlier modifications did).
5. **Shim hash lookup and counters (C2, C3b).**
   - `cb_lookup_hash` (`ft8_shim.c:845`) serves the 22- and 12-bit types today (with the F-001 unique-match suppression for 12 bits). **Add the 10-bit type with the same policy: resolve only when exactly ONE known callsign has that 10-bit hash; ambiguous or unknown => `<...>`.** Unique-match stays because "no name beats a wrong name" (F-001); on a long session it will mostly print `<...>`, and that is expected (section 6, V2b measures it).
   - **The 12-bit code path and its counters stay byte-for-byte as they are.** Their VALUES from this build are nevertheless a NEW F-001 ERA (K1: 0.1 decodes add hound calls to the shared table); say so in the hand-back and in the code comment, so nobody compares them with `main`'s.
   - **New measure-only counter (C3b):** count every CRC-passing candidate that `ftx_message_decode` rejects as an unsupported type, **by (i3, n3)** (`ft8_shim.c` ~l.1888, the place that currently `continue`s). It must not change any output (like SUP-B). Expose it the way the existing SUP-B / F-001 counters are exposed (the same native getter style; `GET /api/v1/status` only if the existing counters are there too; otherwise the native getter and the log line suffice, say which). QA reads it: under chance a false CRC pass lands equally in any of the 64 (i3, n3) codes, and the undefined n3 = 7 cannot be a real transmission, so its count estimates the false 0.1 payloads that reach the decoder.
   - Bump the shim version (next free number: check every `origin/*` ref at work time; at the time of writing `main` is 20260062 and `decoding_improvement` is 20260063) and say which you took.
6. **Do not add encode support** (phase 3). Consequence in section 2.2.

## 2. Managed side
1. **Plausibility filter (C3a)** (`Ft8Decoder.IsPlausibleMessage`, `Ft8Decoder.cs` ~l.1009): a 0.1 text has **5 tokens (4 spaces)** and today hits "R5 Rule B - 5+ tokens ... `spaces >= 4` => false". Add an acceptance for exactly this form and nothing broader: token 0 and token 2 are parsed callsigns (a hashed `<...>`/`<CALL>` is allowed there, see below), token 1 is exactly `RR73;`, token 3 is `<...>` or `<CALL>`, token 4 is a signed two-digit even report in -30..+32. **Tightened from the 288 real rows (HK-038: the population is run `20261009_1752`):** **reject call1 = call2** and **reject a special token (CQ/DE/QRZ) in token 0 or 2** (both counts were 0 of 288). Hashed tokens in 0/2 were also 0 of 288, but they stay **allowed**: rejecting them would remove only about 1.6 % of the random c28 space (the 22-bit hash range) while dropping legitimate non-standard-call hounds, and the degradation rule of section 1.3 needs them reachable; state this in the rule's comment. **Every other 5+ token text stays rejected.** Write it as tightly as the 3-token rules (accept-only, the `IsParsedCallsign` helper from #227/#228, the oversize-token rule D9-R3 applied to tokens 0 and 2).
   **Why this is not enough alone (Architect):** about 98 % of the c28 space is the standard-callsign range, every `r5` value is valid and `h10` always renders, so a random 0.1 payload almost always passes a shape rule; and K1 makes each false 0.1 decode poison the table. Hence the counter of section 1.5 and QA's M2 estimate (section 6). **Add a unit test that measures the rule's acceptance rate on random payloads:** render N (at least 100,000, seeded, fixed seed in the test) random 71-bit payloads through the unpacker and `IsPlausibleMessage` and **report the accepted share** in the test output (no assertion on the number itself except that it is computed; QA uses it).
2. **Subtraction** (`SubtractionPass.cs` ~l.326): a pass-0 decode is re-encoded from its text (`IsReencodable`, `interop.EncodeMessage`). A 0.1 text cannot be re-encoded (no encoder, by design). Make sure it is classed **not re-encodable** (skipped, no exception, not counted as a fit failure), and that the residual pass and the third pass behave exactly as before for every other message. Add a test with a 0.1 decode among others in a scripted pass.
3. **Every consumer of `DecodeResult.Message` text (C4)** must be audited (about 15 sites; start from `git grep -n "\.Message\b" src/OpenWSFZ.Daemon src/OpenWSFZ.Web src/OpenWSFZ.Ft8`): `QsoAnswererService.TryParseMessage` / `TryParseCq`, `QsoCallerService.TryParseMessage` / `TryParseResponder`, the decode-panel mapping and filters (region/callsign attributes), `AllTxtWriter`, `ExternalReportingService`, `EarlyDecodeService` / `EarlyDecodeMatcher`, the cycle archive, `WsjtxDatagram`. **Required behaviour for a 0.1 decode in this task: a displayed and logged row and nothing else.** It must not start, advance, abort or complete a QSO (answerer or caller), must not be taken as a CQ, must not produce an external-reporting spot (check what `ExternalReportingService` does when the region is unknown: it suppresses; prove it for this form), must not make a filter, region lookup or noise-suppression rule throw or mis-attribute a callsign (a 5-token text must not be split into a fake `dest src payload`). **Inert for every batch number (since #249 batches 2 and 3 reach the answerer and caller): one test per service per batch number (1, 2, 3) per relevant state** (answerer: Idle, WaitReport, WaitRr73; caller: WaitAnswer, WaitRr73). WSJT-X-format UDP decode datagrams (GridTracker) for 0.1 rows are a phase 3 question: do not emit them now. Hand back **a table: consumer -> what it does with a 0.1 text -> the test that proves it.** If a consumer would do something other than "ignore", STOP AND REPORT (do not improvise).
4. **Region attribution and noise suppression (C4.2) - a fixed rule for this phase:** the sender of a 0.1 message is the Fox, `call3`. **Region comes from `call3` when it is resolved; otherwise the row is a region-lookup miss, and the existing noise-suppression rule applies unchanged.** Consequence you must not "fix": with noise suppression ON, an unresolved Fox row is hidden. (The Captain decides later whether 0.1 rows should be exempt; build exactly this rule now.)
5. The decode panel and `ALL.TXT` show the text as decoded (same row shape as any other decode, same SNR/DT/frequency fields; `ALL.TXT` line unchanged in format). No new column, no new Settings control.

## 3. Tests (mechanical; synthetic callsigns only, NFR-021; no message text from any real log in the repo)
- 🔴 **C6: test callsigns must be `Q` + DIGIT (`Q1ABC`, `Q2XYZ`, `Q3DX`).** The c28 unpack rewrites `Q` + letter as `3X...` (the Guinea workaround, `message.c` l.812-816), so a `Q`+letter vector renders as `3X...` and fails for the wrong reason.
- **Native/unit:** a constructed 0.1 payload decodes to the expected text for at least 8 vectors: report at both ends of the range (-30, +32, as the paper allows) and a zero/low value; `call3` resolved and unresolved; call1/call2 as ordinary calls and as special tokens (the native unpacker renders them even though the managed rule rejects them); a resolved `call3` long enough to hit the 35-character rule (renders `<...>`); a hashed `call1`/`call2` long enough that step (2) of the degradation is needed. The exhaustive bound test of section 1.3. **Boundary cases (Architect, 2026-10-19):** the real data's longest text is exactly 35 characters and 14 of 288 rows are 33 or more, so the degradation WILL fire on real rows: the bound test must include **a text of exactly 35 characters that is rendered in full (no degradation) and a text that would be 36 characters and is degraded (call3 -> `<...>`)**, both built from real-shaped calls (`Q` + digit, e.g. a 6-character `Q1ABC` hound pair with a resolved Fox call of 10 characters inside the brackets for the 35 case, one character longer for the 36 case; adjust to the actual lengths you construct and assert them).
- **Hash policy:** 10-bit lookup with 0, 1 and 2 matching callsigns in the table => `<...>`, `<CALL>`, `<...>`; and a 12-bit/22-bit lookup test showing the 12-bit path unchanged.
- **Counter:** a rejected unsupported type increments the (i3, n3) cell and changes no output.
- **Plausibility:** the accepted form passes; each of these still fails: a 5-token text that is not this form, `RR73;` replaced by another word, a non-callsign token 0 or 2, call1 = call2, a special token in token 0 or 2, an unsigned or three-digit report, an odd report, a report outside -30..+32, a 6-token text; the existing #226/#227/#228 and D-009 tests pass unchanged. The random-payload acceptance test of section 2.1.
- **Pipeline:** a scripted decode set containing a 0.1 text reaches the panel feed and `ALL.TXT`, is skipped by subtraction (no exception), changes no QSO state (section 2.3, one test per service per batch number per state), and produces no external-reporting spot.
- **No regression:** with no 0.1 payload present, decoder output is byte-identical to `main` (a replay test over the repo's existing synthetic fixtures if one exists; otherwise state how you checked).
- The unfiltered `dotnet test --nologo` passes on Windows and WSL (quote the exact command and totals; a filtered-out suite is not green, HK-022). Do not loosen any existing assertion. Flake rules: `TESTING_STRATEGY.md` section 11.
