## 1. The native unpacker (`native/ft8_lib_vendor/ft8/message.c`, `ftx_message_decode`)
1. Handle `FTX_MESSAGE_TYPE_DXPEDITION` (i3 = 0, n3 = 1) in the `switch` at `message.c:308` (today `default:` returns `FTX_MESSAGE_RC_ERROR_TYPE`). Layout from the vendored table (`message.h:42`): **28 + 28 + 10 + 5 = 71 payload bits** = `c28` (callsign 1) | `c28` (callsign 2) | `h10` (10-bit hash of callsign 3, the Fox) | `r5` (report), then n3 and i3.
2. Rendered text: `<call1> RR73; <call2> <<call3>> <report>`, e.g. `Q1ABC RR73; Q2XYZ <Q3DX> -12`. `call1` and `call2` come from the existing 28-bit unpack (standard calls and the special tokens), exactly as the standard-message path renders them. **`call3`** is rendered through the hash interface by its 10-bit hash (`FTX_CALLSIGN_HASH_10_BITS`, already declared at `message.h:60`): resolved => `<CALL>`, unresolved => `<...>`. **Report `r5`:** a signed two-digit dB report with an explicit sign, `-12`, `+03`; derive the exact mapping from the protocol paper (the range is in 2 dB steps) and **state the formula and the paper section in the hand-back**; QA's replay against WSJT-X's own text checks it empirically.
3. 🔴 **Memory safety is the hard requirement.** The public result field is `message[36]` (max 35 characters: `ft8_shim.h:816`, `Ft8NativeResult.cs:35`, `FTX_MAX_MESSAGE_LENGTH`), and `message.c` uses a fixed `char buf[35]` split into 14/14/6-character fields. A type-0.1 text can be longer than 35 characters (a resolved Fox call is up to 13 characters in brackets). **Do not change the ABI struct.** Rule: if the rendered text would exceed 35 characters, render `call3` as `<...>`; if it still would not fit (cannot happen with standard calls, but prove it), return an error and drop the candidate as today. No write past any buffer, ever; the output is always NUL-terminated. Add a test that decodes **every** value of `h10` and `r5` and a spread of `c28` values (including all special tokens and the hash-form range) and asserts the length bound and the terminator; run it under AddressSanitizer or valgrind on Linux (say which).
4. Keep the vendored file's licence header; mark the added code as OpenWSFZ's (MIT-compatible, your own implementation). Update `NOTICE`/the third-party notes if the repo keeps a per-file modification record for the vendored library (check what the earlier modifications did).
5. **Shim:** `ft8_shim.c:1888` calls `ftx_message_decode` and drops on failure; nothing else should need to change there for 0.1, but check `cb_lookup_hash` (`ft8_shim.c:845`): it serves the 22- and 12-bit types today (with the F-001 unique-match suppression for 12 bits). **Add the 10-bit type with the same policy: resolve a 10-bit hash only when exactly ONE known callsign has that hash; ambiguous or unknown => `<...>`** (1024 hash values make a wrong resolution far likelier than at 12 bits). Do not change the 12-bit counters or behaviour (the F-001 sizing rows depend on them); add separate 10-bit counters only if they are free, otherwise none. Bump the shim version (next free number: check every `origin/*` ref at work time; at the time of writing `main` is 20260062 and `decoding_improvement` is 20260063) and say which you took.
6. **Do not add encode support** (that is for phase 3). Consequence to handle in section 2: the re-synthesis in subtraction goes through the text encoder.

## 2. Managed side
1. **Plausibility filter** (`Ft8Decoder.IsPlausibleMessage`, `Ft8Decoder.cs` ~l.1009): a 0.1 text has **5 tokens (4 spaces)** and today hits "R5 Rule B - 5+ tokens ... `spaces >= 4` => false". Add an acceptance for exactly this form and nothing broader: token 0 and token 2 are parsed callsigns or the special tokens, token 1 is exactly `RR73;`, token 3 is `<...>` or `<CALL>`, token 4 is a signed two-digit report. **Every other 5+ token text stays rejected.** This rule is the only false-positive guard for a payload type that was never produced before; write it as tightly as the 3-token rules (accept-only, the `IsParsedCallsign` helper used by #227/#228, the oversize-token rule D9-R3 applied to tokens 0 and 2).
2. **Subtraction** (`SubtractionPass.cs` ~l.326): a pass-0 decode is re-encoded from its text (`IsReencodable`, `interop.EncodeMessage`). A 0.1 text cannot be re-encoded (no encoder, by design). Make sure it is classed **not re-encodable** (skipped, no exception, not counted as a fit failure) and that the residual pass and the third pass behave exactly as before for every other message. Add a test with a 0.1 decode among others in a scripted pass.
3. **Every consumer of `DecodeResult.Message` text** must be audited (about 15 sites; start from `git grep -n "\.Message\b" src/OpenWSFZ.Daemon src/OpenWSFZ.Web src/OpenWSFZ.Ft8`): `QsoAnswererService.TryParseMessage` / `TryParseCq`, `QsoCallerService.TryParseMessage` / `TryParseResponder`, the decode-panel mapping and filters (region/callsign attributes), `AllTxtWriter`, `ExternalReportingService`, `EarlyDecodeService` / `EarlyDecodeMatcher`, the cycle archive, `WsjtxDatagram`. **Required behaviour for a 0.1 decode in this task: it is a displayed and logged row and nothing else.** It must not start, advance, abort or complete a QSO (answerer or caller), must not be taken as a CQ, must not produce an external-reporting spot (check what `ExternalReportingService` does when the region is unknown: it suppresses; prove it for this form), and must not make a filter, region lookup or noise-suppression rule throw or mis-attribute a callsign (a 5-token text must not be split into a fake `dest src payload`). Hand back **a table: consumer -> what it does with a 0.1 text -> the test that proves it.** If a consumer would do something other than "ignore", STOP AND REPORT (do not improvise).
4. The decode panel and `ALL.TXT` show the text as decoded (same row shape as any other decode, same SNR/DT/frequency fields; `ALL.TXT` line unchanged in format). No new column, no new Settings control.

## 3. Tests (mechanical; synthetic `Q`-prefix callsigns only, NFR-021; no message text from any real log in the repo)
