## 0. Why this session exists

`F-001`'s hashed-callsign resolution correctly *resolves* a nonstandard callsign hash to a
real callsign string, printed as `<CALL>`. But nothing downstream ever consults that
resolution when deciding whether a message is addressed to us: `TryParseMessage` requires
exactly 3 space-separated tokens (a 2-token Type-4 shorthand like `<CALL> RR73` fails to parse
and the whole decode is silently skipped — **L1**), and even when it does parse, the
`dest`-vs-`ours` comparison is a literal string compare, so a correctly resolved `<PD2FZ>`
never equals `PD2FZ` — **L2**. `git blame`/design review (`qa/rr-study/2026-08-27-1531-*.md`
Sec.0.1) confirms route 5 as originally proposed on GH #60 ("hash our own callsign, compare
directly") is a **no-op**: L3 (the hash comparison) is never reached because L1/L2 already
discard the message.

The `F-001 R5` measurement arm (`qa/rr-study/2026-08-27-1603-*.md`,
`qa/rr-study/2026-08-27-1615-*.md`) confirmed the reframing is correct (G1 HOLDS: today's
predicate recognises zero hashed-`dest` decodes as "to us"; L1+L2 recognises hundreds) but also
found that stripping brackets (L2) is not free: it makes an *already-misresolved* hash
**actionable**, promoting an existing harm 1 (wrong name displayed) into harm 2 (an
unsolicited transmission to a station that did not call us). Measured false-positive rate
when an own-hash-equivalent fires, no partner bound: **CP one-sided 95% lower bound 71.02%**
— wrong roughly 3 times in 4, against an a-priori base rate of 1-in-4,096. The PO reviewed this
and ruled: ship L1+L2 now (bench/unit only, no transmitting run — we are structurally unable to
measure benefit offline, `Tx=0` in every artefact we hold), defer L3 (the actual own-hash
compare, needs a shim/ABI change) to a second slice, and require this slice to make an
**explicit, recorded** decision about whether L1+L2 fire in the unengaged state, where the
benefit lives but so does nearly all of the measured cost.

**Behaviour change intended:** the answerer and caller will recognise 2-token Type-4 replies
and bracket-wrapped own-call references as "addressed to us" in the **partner-bound** states
(`WaitReport`, `WaitRr73` on both sides). Whether the **unengaged** state (`QsoCallerService`
`WaitAnswer` — waiting for someone to answer our CQ) also gets this recognition is the decision
in Section 3. **No change to any displayed or logged callsign string is intended** — see the
constraint in Section 2.

## 2. Implementation shape — pick one, and the constraint that binds either way

Two shapes are available (Architect's brief Sec.3). **Developer's call with the Captain** —
but it must be a recorded decision, not a side effect discovered in review.

**(A) Normalise at the parse boundary.** Strip one `<`/`>` pair and accept a 2-token form
inside both `TryParseMessage` copies (sites 1/2) plus, if Section 3 extends to it, site 6.
Smaller diff, one place to reason about the guard (Action 2.4 below).
🔴 **Cost:** `dest` reaches a log call at `QsoAnswererService.cs:~1131` (`"{Partner} is
working {OtherDest}"`, using `dest`). Normalising at the boundary **changes that log line's
text** for a message that used to log `<PD2FZ>` and will now log `PD2FZ`. This is not a
*displayed* name (the R5 ruling's "no change to any displayed name" promise is about the UI/
ADIF surface) but it is close enough that it must be a decision, not a side effect. **If (A)
is chosen, add a one-line code comment at the log call noting the normalisation moved
upstream, and pin the new log text in a test (Action 4.5).**

**(B) Normalise at each comparison site.** Sites 3/4/5 (and site 6, if extended) each strip
brackets locally, right before the `.Equals()` call; `TryParseMessage`/`TryParseResponder`
keep returning the raw token. Logs stay byte-identical. **Cost:** sites 3/4/5 (and 6, and both
independent `TryParseMessage` copies for the 2-token acceptance) must all move together —
fixing a subset is a defect, not a partial fix. Consider a single shared static helper (e.g.
`QsoMessageParsing.NormalizeDest(string dest)`) to make "all sites moved" mechanically
checkable rather than relying on review to catch a missed call site.

**Constraint, either way:** the `<...>` all-dot marker (native encoder's failure-to-resolve
output, `message.c:604-611`) is **not a callsign** and must never compare equal to anything —
not to a real callsign, not to another all-dot marker, not to an empty string. This is the one
line where a mistake is silent and severe: a bug here turns "we could not resolve who this is"
into "this is addressed to us." Guard: reject `dest` that is empty after stripping, or whose
stripped content is entirely `.` characters, before doing the equality compare.

## 3. STOP AND DECIDE — the unengaged-state (site 6) decision

🔴 **This is a PO/Captain decision (per the R5 ruling and the Architect's brief Sec.4), not an
implementation detail QA or the Developer can settle by default.** The Captain must record an
explicit answer to the question below — in this file's Section 7 QA/Captain notes, or in the
commit message of the change that resolves it — before `TryParseResponder` (site 6) is
touched. **If this is not recorded, the Developer session must leave site 6 unchanged** (the
safe default: sites 1–5 only) and say so explicitly in the handoff back to QA — leaving it
unchanged silently, without saying so, is not an acceptable outcome either.

**The question:** should L1 (2-token parse) and L2 (bracket-strip) apply to `TryParseResponder`
(`QsoCallerService.cs:1374-1417`, `HandleWaitAnswerAsync`, the **unengaged** — no partner yet
bound — state)?

**The evidence, both directions, stated together (do not silently pick one side):**

- **Against:** in this corpus, when an own-hash-equivalent rule fires with no partner bound,
  it is wrong roughly **3 times in 4** (`F-001 R5` G3 MIN, CP one-sided 95% lower bound
  **0.7102** — 14× past the arm's own 0.05 "unfavourable" bar — against an a-priori base rate
  of 1-in-4,096 = 0.000244). Site 6 is exactly the place a false fire has no `fromPartner`
  conjunction to contain it: acting on it means **transmitting an unsolicited signal report to
  a station that did not call us.**
- **For:** a fire is rare in absolute terms — 129 of 11,233 hypothetical own-calls in the
  corpus take any false fire across 4 days, mean 0.084, median 1 among those affected; our own
  actual call observed **0** false fires (⚠️ λ = 0.379 under Poisson — HK-021(j): a zero
  observation here is not evidence of absence, not a clean pass). And the unengaged state is
  **precisely** where the benefit lives: a correspondent answering our CQ with a nonstandard
  callsign is the scenario route 5 exists to fix. Restricting L1+L2 to the partner-bound sites
  (1–5) is safe but guts most of route 5's value — nearly all real recoveries happen after a CQ,
  before a partner is bound.
- **What is NOT available as a resolution:** waiting for L3 (the actual hash comparison,
  second slice) does not make this decision go away — L1+L2 alone, at site 6, already carry
  the SAME false-fire mechanism (a resolved-but-wrong `<CALL>` becomes actionable the moment
  brackets are stripped; see `qa/rr-study/2026-08-27-1615-*.md` Sec.6.2 — "L2 has L3's
  false-positive rate with a lower firing rate, not a different failure mode").

**Options the Captain may choose between (not exhaustive — record whichever is actually
decided):**

1. **Restrict to partner-bound only this slice.** Sites 1–5 change; site 6 does not. Ships the
   safe, already-measured part now; the unengaged-state benefit waits for a mitigation (e.g.
   L3's own-hash compare with a same-code-collision check, or an operator confirmation prompt)
   in the second slice.
2. **Extend to site 6, accepting the measured risk**, on the strength of the "rare in absolute
   terms" evidence. If chosen, the acceptance criteria (Section 4) must add a test asserting
   the unengaged-state fire path is reachable and behaves as decided — do not let it be an
   accidental consequence of a shared-helper refactor.
3. **Extend to site 6 with an added mitigation** — e.g. require the resolved name to be
   accompanied by something the current message already carries (a signal report or grid in
   the third token, which `TryParseResponder` already validates) as a weak second signal, or
   surface a clearly-marked "resolved from hash, unconfirmed" state to the operator rather than
   auto-transmitting. Design is the Developer's, subject to Captain sign-off; whatever is
   chosen must be testable per Section 4's shape (a hard, mechanical assertion).

## 4. Actions

### 4.1 — `QsoAnswererService.cs`: extend `TryParseMessage` to accept the 2-token Type-4 form (L1)

`TryParseMessage` (line 1631) currently requires `parts.Length == 3`. Add acceptance for
`parts.Length == 2`, returning `dest = parts[0]`, `src = parts[1]`, `payload = ""` (matching
the R5 harness's own transcription, `qa/rr-study/2026-08-27-1531-*.md` Sec.3.2). An empty
`payload` must not crash any downstream `payload.Equals(...)` check (it already won't — those
are simple string comparisons against non-empty literals — but confirm by running the full
`QsoAnswererServiceTests` suite, not just the new tests).

### 4.2 — `QsoCallerService.cs`: the same change to its independent `TryParseMessage` copy (L1)

Line 1349, same acceptance. **These are two separate copies of the same function — a
single-copy fix is a defect** (Action 4.6 / AC-1 below is the mechanical check for this).

### 4.3 — Normalise `dest` before the L2 comparisons, per the shape chosen in Section 2

Sites 3 (`QsoAnswererService.cs:1079`), 4 (`:1161`), 5 (`QsoCallerService.cs:938`). Strip one
leading `<` and one trailing `>` before the `.Equals(ours, StringComparison.OrdinalIgnoreCase)`
compare; apply the all-dot/empty guard from Section 2 first. If shape (B), do this locally at
each site (or via a shared helper called from each site); if shape (A), do it once inside both
`TryParseMessage` copies and remove the need for per-site changes to 3/4/5 (sites 7/8 then see
the normalised value too — confirm this is what was decided, Section 2).

### 4.4 — Site 6 (`TryParseResponder`), gated on Section 3's recorded decision

If Section 3 resolved to "restrict to partner-bound only" (option 1): **make no change to
`TryParseResponder`.** Add a code comment at the function referencing this task and the
Section 3 decision, so a future reader does not assume the omission was an oversight.

If Section 3 resolved to extend (options 2 or 3): apply the same 2-token acceptance and
bracket-strip/guard logic, plus whatever mitigation option 3 specifies. `TryParseResponder`
already has its own compound-vs-base normalisation (lines 1389–1394) immediately before the
`parts[0]` comparison — extend that same block rather than adding a fourth, independent
comparison.

### 4.5 — Pin the Section 2 log-line decision in a test

If shape (A): a test on `QsoAnswererServiceTests` (or a new focused test) drives a
`fromPartner && !toUs && !dest.Equals("CQ")` abort with a bracket-wrapped `dest` and asserts
the log message contains the **stripped** callsign, not the bracketed form. If shape (B): the
equivalent test asserts the log message is **unchanged** (still bracketed). Either way, the
choice must be visible as a passing, named test — not left to be noticed only in manual
review of a log line.

### 4.6 — Regression + new coverage

- A test asserting **both** `TryParseMessage` copies (`QsoAnswererService` and
  `QsoCallerService`) accept the 2-token form identically — e.g. a small shared theory/data
  test if the project's xUnit conventions support one, or two mirrored tests if not. This is
  the mechanical check that a single-copy fix fails: if only one copy is updated, this test
  fails.
- A test asserting `<...>` (all-dot) as `dest` never yields `toUs == true`, for at least one
  own-call including the case where the hypothetical own-call is itself `"..."` (degenerate
  edge, cheap to cover, catches a same-string-both-sides bug).
- A test asserting `<Q1OFZ>` (bracket-wrapped, using the project's existing NFR-021 synthetic
  own-call convention — see `QsoAnswererServiceTests.cs`'s `OurCallsign = "Q1OFZ"`) as `dest`
  with `ours = "Q1OFZ"` yields `toUs == true`, and with `ours = "Q1OFZQ"` yields `false`
  (exercises L2's own string boundary — a naive substring-contains bug would pass this
  differently than an exact-match-after-strip implementation).
- A test asserting the existing compound-vs-base precedent (`Q1OFZ/P` → `Q1OFZ` at site 6)
  still passes unmodified — this is the regression check for "L2 broke an existing
  normalisation."
- Full `dotnet test`: 0 failures, including all newly added tests.

### 4.7 — Post-build acceptance gate: the zero-fire corpus replay

Replay `artefacts/20260803_live_run_1713/owsfz` through the new build with
`ourCallsign = PD2FZ` (the real corpus's actual own call — this replay step operates on
already-committed-safe local artefacts and produces no new committed output; NFR-021 still
applies to anything written to a committed file). **The answerer must fire `toUs` exactly zero
times.** Rationale: `PD2FZ` occurs zero times as a plain token in either log in this corpus
(`qa/rr-study/2026-08-27-1615-*.md` Sec.a confirms independently), so it can never have entered
a hash table and can never be printed as a resolved `<PD2FZ>` — the correct answer is a hard
zero. Any non-zero fire is either a bracket-guard defect (Section 2's constraint broken) or a
misresolution reaching the comparison in a way this task did not anticipate, and either is a
STOP condition, not a result to report and move past. This gate needs the built binary but
**no transmitting station**, consistent with the PO's bench-only scope for this slice.
