## 0. Why (one paragraph)

WSJT-X's AP type 1 assumes a message starts with `CQ`. Our decoder uses AP only for QSO context (`ft8_set_ap_bits`). The Captain wants to know whether a CQ-AP attempt, tried **in addition** on candidates that failed, finds real weak CQs. QA measures it by an OFF/ON replay against PSK Reporter and WSJT-X (QA's job). **Your build only has to be correct, off by default, and measurable.** The station never runs it live in this test.

## 1. What to build (line numbers on `98332f2a`; they drift)

| row | requirement |
|---|---|
| **D1 Bits (spec A1.2: injected AFTER normalisation)** | The CQ-AP attempt forces **payload bits 0 to 28** (`n29a` = c28("CQ") `<< 1` \| `ipa` 0; c28("CQ") is 2 in ft8_lib's `message.c`; read the constant there, do not retype it) **and bits 74 to 76** (`i3` = 1): 32 positions, no others. Layout: `[0,29)` call 1 (28-bit c28 + ipa), `[29,58)` call 2, `[58,74)` ir + grid, `[74,77)` i3 (`message.c:156-208`, `:354-397`). Sign convention is the BP one: **bit 1 = positive LLR** (`ldpc.c:68`), bit 0 negative. **The forced LLRs are written after `ftx_normalize_logl`, at magnitude 1.01 × the largest \|LLR\| of the normalised non-forced entries.** This is deliberately NOT the QSO-AP form (`decode.c:1100-1106`, ±40 before normalisation, whose variance effect is recorded as observation O2 and is out of scope). **QSO-AP's path, scaling and results must not change.** |
| **D1 test (the authority)** | A unit test encodes `CQ Q1ABC JO22` with ft8_lib's own encoder (`ft8_encode_message` / `ftx_message_encode`) and asserts that **every overridden position equals the encoded bit**, and that exactly 32 positions are overridden. The tests exist because earlier AP work had position and sign errors (E151/E152). |
| **D1b Sign test** | On a clean encoded `CQ Q1ABC JO22` (LLRs from the codeword, noise-free): with the right-sign override the CQ-AP attempt decodes; with the **opposite-sign** override it does not. |
| **D2 Flag** | New decoder key **`cqApEnabled`**, bool, **default `false`**, read once per cycle like `coherentFallbackEnabled` / `coherentFallbackMultiSet` (`DecoderConfig.cs`, `Ft8Decoder.cs`, the daemon wiring). **Config POST is an overlay (HK-035): a partial post leaves it as it was (test).** No Settings-page control. It reaches native as a **per-call bit/flag, not a process-global** (model: the multi-set flag in `ft8_coherent_fallback_run`'s `flags`; for `ft8_decode_all` use whatever per-call carrier exists or a new thread-local set in the same bracket as the other per-call settings, and say which). **With the flag OFF, decode outcomes on a fixed WAV set are identical to `98332f2a`** (mechanical diff of outcome fields: text, freq, dt, SNR, pass, path; never rendered text), including with QSO-AP active. |
| **D3 Extra, never instead (spec A1.5)** | The CQ-AP attempt runs **only on a candidate whose normal attempt failed** (the normal attempt includes QSO-AP when active), in **every pass** of `ft8_decode_all` and on **every buffer it is called on** (original, residual, third-pass buffers). It never replaces a normal attempt. **Placement: it is part of the `decoded` determination, BEFORE the `if (!decoded) { ...; continue; }` branch** (`ft8_shim.c` around `:1875-1900`). A CQ-AP decode therefore goes through the existing cross-pass dedup, `ftx_message_decode`, the hash handling and `results[]`, **sets `tls_cf_cands[cf_slot].decoded` and stores its payload** (`tls_cf_payloads`), so the coherent fallback does not retry that candidate. The coherent fallback itself is out of scope. |
| **D4 BP only (spec A1.5)** | The CQ-AP attempt runs **belief propagation only; OSD is never run on it.** `ftx_decode_candidate_ap` falls back to OSD internally (`decode.c:1118`), so write a **BP-only variant or a parameter** that cannot reach `osd_decode`, and a **real counter** (thread-local, with a getter) of OSD entries from the CQ-AP path. A test reads it as **0** after a run in which the OSD would have been reachable (prove it can count: a test-only hook or a test copy that does enter OSD must read > 0). Same BP iteration limit as the normal attempt. QSO-AP keeps its OSD fallback unchanged. |
| **D5 Filter unchanged** | CQ-AP decodes pass the same CRC, `IsPlausibleMessage` (`Ft8Decoder.cs:1461`, applied at `:803`) and text dedup as any decode. No new acceptance path, no new gate. |
| **D6 Tag and log** | Every decode carries **`apKind`** (`none` = 0, `cq` = 1): in the native result (append a field with the C# struct changed in the same commit, or a new struct; existing exports' contracts unchanged), through the interop to the managed decode record, and to the **replay harness output** (QA adds the column; you expose the field). **One Information log line per cycle, only while `cqApEnabled` is true:** `cq-ap: attempts=N decodes=M` (N = CQ-AP attempts, M = CQ-AP decodes published; counts only, never a callsign). With the flag OFF there is no new log line. |
| **D7 Not uploaded** | Decodes with `apKind = cq` are **not uploaded to PSK Reporter**: a new counted exclusion reason **`ap=`** in `PskReporterEngine`, added to both accounting lines ("PSK Reporter: N decodes seen, M reported: region=..., ap=N" and the per-datagram line) and to whatever status counters carry the other reasons. Existing tests that pin those line formats change in the same commit (list them with FILE:LINE). `ALL.TXT`, UDP and panel formats are unchanged (the flag is not ON live in this test). |
| **D8 Harness (QA's side)** | QA adds `--cq-ap on\|off` to Replay81 and the `apKind` column, after your report names the interop setter and the field. **Your job: expose them and name them in the report** (property, interop method, native export, struct and field). |
| **D9 Provenance** | `FT8_SHIM_VERSION` bumped with a history entry; report the built `libft8.dll` SHA-256 (`tools/check_native_version.py`). Build the Windows DLL as the repo's own scripts do (`native/ft8_lib_build/rebuild_shim.bat`), and keep the C portable (the same sources build `libft8.so` and `libft8.dylib`; no MSVC-only constructs). The committed Linux and macOS binaries are refreshed by the usual follow-up chore after the native merge (PR #254 did it for 20260069): **state the step in your report so QA does not meet a stale binary in CI.** |
| **D10 Synthetic tests (Q-prefix calls only)** | (a) a `CQ Q1ABC JO22` at an SNR where the OFF build fails is decoded by ON with `apKind = cq` (pick the SNR from a short sweep and say how); (b) a non-CQ `Q1ABC Q2DEF JO22` is **never** decoded with `apKind = cq` (with the flag ON); (c) noise-only audio gives **0** `cq` decodes over >= 200 cycles with the flag ON. **The SNR sweep with Wilson intervals (spec A1.3: 1 dB steps from OFF's 50 % SNR minus 4 dB to plus 1 dB, >= 200 cycles per step, bar >= 10 pp ON minus OFF with separated intervals) is QA's acceptance run on your build, not your test:** your tests only need to be able to fail.
