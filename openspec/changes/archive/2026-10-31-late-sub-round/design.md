## Decisions

**D1. C#-only, behind a setting, default OFF.** The effect is established on one fresh night (NET +0.742 pp, CI lower bound 0.621) and on the refset night; a default change waits for the third night on sol and the Captain. OFF must be byte-for-byte today's behaviour (acceptance row B-OFF).

**D2. No native change.** The round is `SubtractionPass.RunThirdPassAsync` called a second time with a different buffer and fit list; the native entry points are the ones the third pass already uses. If the Developer finds a native change unavoidable, STOP and return to QA.

**D3. When it runs (spec R2 with F2).** Setting ON, a staged cycle, depth Deep, the coherent fallback ran this cycle (`fallbackReady`, whether or not it published), and `CohFallbackAudioSelector.Select(audioMode, normalisedPcm, deepForFallback, reportForFallback, thirdResult)` (the same call the fallback makes, so the two cannot drift) returns a residual buffer (`IsResidual`). Each other case is a counted, logged skip: `skipped-normal-depth`, `skipped-fallback-not-run`, `skipped-nothing-decoded` (pass 0 decoded nothing), `skipped-no-residual` (Select returned the original audio: mode `Original`, the residual pass abandoned or failed, or nothing fitted). Select's own rules already cover "the residual pass was not abandoned and did not fail" (R2(d)).

**D4. Buffer B, no copy (F2).** B is what `Select` returned: the third pass's own subtracted buffer (R3) or the residual pass's (R2). The fallback may still hold references to it, so the round must not write to it. `RunThirdPassAsync` documents its input as not modified (`SubtractionPass.cs:215-216`) and `RunCore` clones before subtracting (`SubtractionPass.cs:425`, `var residual = (float[])normalisedPcm.Clone()`); a test checks that the array the fallback was handed is unchanged after the round.

**D5. The fit list is what `MapNative` published (F1).** The harness's rule, and the one the first spec text got wrong, is: the natives behind the decodes `MapNative` returned in batch 3 and batch 4, i.e. the first occurrence of each text in the cycle, not already in `seen`, `IsPlausibleMessage` true. `MapNative` gains an optional `List<Ft8NativeResult>? keptNatives` that receives the native behind each decode it adds; the batch-3 call and the batch-4 call pass a list (and pass none while the setting is OFF, so the OFF path is the code as it was). `FreqHz` is the native's own (batch 4: `round(OutFreqHz)`), `Dt` is `OutDtS` unrounded, as the fallback builds the native. `alsoKnown` = batch-1 natives ∪ the raw batch-2 natives (`newFromResidual`); batches 1 and 2 are known to the pass's payload dedup, not re-fitted. Fit entries that fail `IsReencodable`/`EncodeMessage` are skipped exactly as in the third pass; `refused` = fit entries minus the pass's `FittedSignals` (the re-encodable count), `-1` when the pass failed before counting.

**D6. The call and the budget (R4).** `SubtractionPass.RunThirdPassAsync(_interop, B, fit, alsoKnown, EffectiveSubtractionThreads, _logger, _apConstraints, SubtractionCycleBudget - sw.Elapsed, ct)`: the third pass's budget arithmetic. No new constant: the pass's deadline and reserve logic is the time guard, all-or-nothing, so an abandoned round publishes nothing. The pass writes its own `Third pass:` line as it does for the real third pass, so a cycle with the round carries two such lines; the `Late subtraction round:` line is the one that identifies the round. An empty fit list does not call the pass (it would decode an unchanged buffer): outcome `no-new`.

**D7. Outcomes.** `ran` = the pass completed (also with `new=0`); `no-new` = nothing re-encodable to subtract (the pass's `skipped-no-new`) or an empty fit list; `abandoned` = the deadline; `failed` = a contained exception. Counters beside `_thirdPass*`: runs (started a fit: ran, abandoned, failed), skipped (every `skipped-*`), no-new, abandoned, failed, decodes.

**D8. Publication (R5 with F4).** The round's decodes go through `MapNative(…, PathResidual)` with the cycle's `seen` set (a text already published in any batch is dropped) and are handed off as batch 5 through the existing `onFallbackBatch` delegate (`DecodeStagedAsync` already forwards the number: `(number, batchF) => publishBatch(number, batchF)`; `DecodePump`'s staged delegate sends every number other than 1 to `PublishSecondAsync`). Only when non-empty, and only after the fallback's batch was handed off, so batches 1 to 4 and their timing do not move. A late batch 5 reaches the panel, `ALL.TXT` and reporting but can arrive too late to affect that cycle's TX decision, as batch 4 can today.

**D9. Hash-table ordering (R5).** The round's native decode unpacks messages through the process-global callsign hash table. It starts after `RunCoherentFallbackBatchAsync` returned, so after the fallback's `CohFallbackUnpack` (the fallback's only hash-table access), and the pump holds the decode gate across the whole `DecodeStagedAsync` call, so the round is the cycle's last hash-table access. A test records the native call order and requires `unpack` < the round's decode < `batch5`. Consequence for acceptance: ON can legitimately resolve a `<…>` token differently from OFF in a later cycle (hash-table feed-forward), so row B-EQ-1 compares batches 1 to 4 exactly up to the first cycle with a batch 5 and modulo hashed tokens after it (spec Amendment 1, F3).

**D10. The log line (R6).** One per Deep cycle while the setting is ON (a Normal-depth cycle writes the `skipped-normal-depth` line): `Late subtraction round: outcome=…, buffer={R3|R2|-}, fit=N, refused=N, new=N, published=N, fbEndMs=…, startMs=…, elapsedMs=…, endMs=…, batch=5, batch5PublishMs={…|-1}.` Times are milliseconds on the decode's own clock (`BudgetClock`, as `fbStartMs`): `fbEndMs` is when the fallback's work including its hand-off returned (-1 if it did not run), `startMs` when the round began, `endMs` when its work and mapping finished (before the hand-off), `elapsedMs` = `endMs` - `startMs`, `batch5PublishMs` the instant before the hand-off. Aggregates only: no message text (HK-037).

**D11. Config.** The key follows `decoder.coherentFallbackResidualUngated`: `DecoderConfig`, a volatile field set by the daemon before the first window and on every config save, read once per window, overlay semantics of HK-035 (a partial post leaves it as it was), no Settings-page control.

## Risks

- A fit-list error (the first spec text took batch 3 raw). Mitigation: the F1 test (a repeated text and an implausible text in batches 3 and 4 are not fitted); acceptance row B-EQ-2 compares batch 5 with the harness's published rows.
- Time: the round runs after the fallback and takes the cycle's remaining budget. sol's fallback ends at about 11.1 s of 13 s, so the round may be abandoned there; the verdict night runs on sol, so NET prices it.
- More published decodes when ON, uploaded to PSK Reporter without a per-batch filter. Mitigation: default OFF; for the Captain at the default decision.
- Hash-table feed-forward makes a strict OFF/ON comparison of later cycles wrong on hashed text. Mitigation: F3.
