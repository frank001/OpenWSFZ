## Context

The pipeline is a fire-and-forget capture start (`captureManager.StartAsync`) plus one `CycleFramer` task. Today both live as top-level locals and local functions of `Program.cs` (`framerCts`, `framerTask`, `restartSemaphore`, `StartPipeline`, `StopFramerAsync`, `RestartPipelineAsync`, and the `OnSaved` handler with its `runningDevice` / `runningEnabled`), which no test can reach. `CaptureManager.Samples` is one channel for the life of the process (`SingleReader = false`); an orphaned framer keeps reading it. `framerOutput` and `earlyOutput` are `SingleWriter = true`. The Architect's spec is `qa/rr-study/2026-10-26-1810-architect-to-qa-spec-266-orphaned-cycleframer.md` on `arch/framer-266` (§11 Amendment 1 adopts QA's K1 to K4); QA's (k) review is `qa/rr-study/2026-10-26-1900-qa-to-architect-k-review-spec-266-orphaned-cycleframer.md`. Precedent: `CaptureAutoStartCoordinator` was extracted from `Program.cs` (#187) so its rules could be tested; this change does the same for the rest.

## Decisions

1. **One owner, injected collaborators.** A `PipelineController` in `src/OpenWSFZ.Daemon/` owns the framer slot, `CycleFramer` construction, capture start/stop, the monitor resets and the semaphore. Collaborators come in as delegates or small interfaces (config reader, capture start/stop, a framer factory returning a stoppable handle, the three monitor resets, a logger), as `CaptureAutoStartCoordinator` does, so every rule is unit-tested with fakes and no network, audio device or clock. `Program.cs` only constructs and wires it.
2. **Level-triggered, reading the current configuration inside the semaphore.** `ReconcileAsync(reason, forceRestart)` reads the configuration after acquiring the semaphore, so the order in which queued calls run does not matter (closes F3). The save handler calls it once when the device or `DecodingEnabled` changed; calling it on every save would also be safe (converged means no action) but would give an unrelated save a chance to act, so QA keeps the change-trigger.
3. **"Running" is the owner's record, not capture health.** A dead capture with a started record counts as running; the capture-recovery coordinator's backoff owns its retry and calls `ReconcileAsync("capture-retry", forceRestart: true)`. Otherwise an unrelated save could bypass the backoff. `forceRestart` while decoding is off does nothing (T5).
4. **D1 = a: a device change while decoding is off is saved only.** No capture, no framer, no decode. This matches startup, `decode/stop` and the coordinator's own guard (`CaptureAutoStartCoordinator.cs:119`). The level meter and waterfall are driven by capture chunks (`Program.cs:244-248`), so they are already idle on those paths; the only visible change is the device-change case. `CaptureRecoveryState.DeriveCaptureState` already reports `Idle` when decoding is disabled.
5. **The start step is defended (R4), not relied on.** It stops any framer found in the slot before starting, and logs one Warning if it had to. Reconcile stops first on every normal path, so the Warning is reachable only through the defence; its sole direct test is T8, and every other test asserts the Warning count is 0 (K4). The Warning contains no callsign or message text.
6. **Observable by log.** `Pipeline started on '{Device}' (reason: {Reason}).` and `Pipeline stopped (reason: {Reason}).` at Information; starts minus stops is the number of framers (0 or 1). The existing `Starting FT8 pipeline` and `CycleFramer started` lines stay (QA's counters read them).
7. **Keep `captureManager.StartAsync` fire-and-forget.** Capture faults arrive through `CaptureFailed`; the controller must not turn the start into an awaited call that can hold the semaphore while a device opens.
8. **Delete the edge-trigger state.** `runningDevice` and `runningEnabled` go; two records of "what is running" is how F3 arises.
9. **Shutdown keeps today's order** (health monitor, framer, decoder dispose, capture) under the same semaphore, so it waits for an in-progress reconcile.
10. **Single-owner grep (Q2).** On the reviewed commit, `new CycleFramer(`, writes to the framer slot, `captureManager.StartAsync` / `StopAsync`, `runningDevice` and `runningEnabled` occur only in the controller (and tests).
11. **L1 is a scratch instance, not the station.** Its own port and config under `D:\Projects\claude\_qa-scratch\framer-266\`, a replayed WAV on a Voicemeeter bus as the audio source (deterministic, no radio), the main daemon untouched. Script: start with `decodingEnabled: false`; choose the device and save; **wait 4 cycles**; Start; read 20 cycles; Stop, Start; read 20 more. Counts only from the logs (NFR-021, HK-037).

## Risks

- **The F2 bar passes vacuously on a silent source.** Mitigation (K1): L1-a on the defective build must show at least one decode in cycles 2 to 4 before Start; L1-b then claims 0 only if the same instrument saw decodes there.
- **A mutation that no test can kill** (m1, m3, m5). Mitigation (K3, K4): T3 changes the configuration between the trigger and the semaphore acquisition; T8 asserts the stop-before-start order and exactly one Warning; all other tests assert zero Warnings.
- **The duplicate-stamp bar's instrument is unvalidated.** Mitigation (K2): QA's counter must reproduce the 8081 log's figure (the Architect counts 29 duplicated of 62 distinct stamps in 91 windows; the issue said 29 of 61) before L1-a is read.
- **Behaviour change for the operator**: a device chosen while decoding is off leaves the waterfall dark. Stated in the release note.
