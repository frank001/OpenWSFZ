In `PskReporterService.ApplyConfig` the offset is `_firstSendOffset()` passed to `_engine.Activate`; replacing it with `TimeSpan.Zero` leaves all 63 PSK tests green. **Add a service-level test** with an injected offset (the constructor already takes `firstSendOffset`): with records queued and the offset 42 seconds, nothing is sent at 41 seconds and the first datagram goes at 42; and a second enabled period (disable, enable) takes a fresh offset from the delegate. Then QA repeats Q31 and expects it killed. ## Findings for rulings (not Developer work)

- **N-1 NFR-021(3) was amended by the Developer, and the premise of D1 was not what NFR-021(3) says. The Captain should see the new wording before merge.** The original (3) reads: "Personal data captured at runtime (decoded callsigns, ALL.TXT) is processed locally on the operator's own machine, **is not transmitted off-host (NFR-004)**, and is retained solely at the operator's discretion". The Architect's D1 text said NFR-021 "says nothing about an operator-chosen upload"; it does. The Developer added a narrow exception clause: "(NFR-004) except by the opt-in PSK Reporter upload (FR-088 to FR-094), which sends the calls and locators of received stations, with the operator's own call and locator, to the public PSK Reporter service only while `pskReporter.enabled` is true (default false; the service logs counts, never calls)". The wording is accurate and as narrow as it can be, and it was the right thing to do (the code would otherwise contradict a Must Have requirement), but it is a change to a privacy requirement the Captain decided on a premise that was incomplete.
- **N-2 `<to> <from> R <grid>` (4 tokens) is not reported.** The Developer made the standard form exactly three tokens. A reply with an R-prefixed grid (`R JO22` as two tokens) is a standard message whose sender and grid are valid spot data (more common on VHF contests than on HF); the amended spec (A1.2) says "the standard form gives token 1". Recommend the Architect rule: report it with the grid (a small, safe change), or accept the deviation as conservative and state it.
- **N-3 A dial outside the amateur band table is keyed as band "unknown" and still reported.** The spec is silent. `AdifLogWriter` has the same "unknown" fallback, but a public spot on a non-amateur frequency is worse than a missing one. Recommend the Architect rule: do not report (count it with "no dial frequency").

## Advisories (no change required)

- **A-1** `ApplyConfig` runs in `StartAsync` and on every config save with no `try`/`catch`; `JsonConfigStore` invokes `OnSaved` unguarded, so an exception from the socket factory would fail a Settings save (the file is already written) or the daemon's start. The existing `ExternalReportingService` handler has the same exposure, so this is the project's pattern; a `try`/`catch` logging one Warning is cheap.
- **A-2** No test pins "early-decode preview rows never reach the service" (the Developer said so). It holds structurally (the pump publishes early rows to the panel only, and writes the reporting queues only in `PublishFirstAsync` and `PublishSecondAsync`); a pump test with an early coordinator would guard a future regression.
- **A-3** The Settings hint names only the placeholder `Q1OFZ`; the rule is any Q-prefix call. Cosmetic.
- **A-4** An invalid `pskReporter.port` (file-only) makes every send throw and log one Warning per window, forever; contained, no validation. Acceptable for a file-only setting.
- **A-5** The Developer's decision list (unknown dial reports nothing; strictness; 254-byte cut on a character boundary; queue 1,000; sequence and session id kept across a disable/enable while the socket, template cadence and first-send offset restart) is consistent with the amended spec, except N-2 and N-3 above.
