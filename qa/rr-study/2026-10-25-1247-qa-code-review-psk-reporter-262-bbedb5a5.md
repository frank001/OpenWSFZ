## Required change

- **R-2: `PskReporterService` must be safe to stop after it has been disposed (and to stop or dispose twice).** In the third full-suite run QA made on `bbedb5a5` (`dotnet test OpenWSFZ.slnx`, clean tree), **one Web test failed: `FR-074: D1: an explicit null on a non-nullable scalar is still a 400`**, with `System.ObjectDisposedException : The CancellationTokenSource has been disposed.` at `PskReporterService.StopAsync` (`_stopCts?.Cancel()`, line 91) called from `WebApplicationFactory.DisposeAsync` → `Host.StopAsync`. The same Web project had passed 410 of 410 on both earlier commits; the increment did not touch the Web project; QA then ran that test class 20 times on a quiet machine with 0 failures. So it is **intermittent**, depends on the order in which the test host's teardown reaches the service, and is a **defect of the new service** (it makes an unrelated test class flaky). It reproduces deterministically in isolation: QA's scratch test `StopAfterDispose_DoesNotThrow` (service started, `Dispose()`, then `StopAsync`) fails with exactly that exception, while stopping twice and disposing twice passes. `Dispose()` disposes `_stopCts` and `StopAsync` then calls `Cancel()` on it.
  **Add the two tests** (stop after dispose does not throw; stop twice and dispose twice do not throw: `qa/rr-study/results/2026-10-25-psk-reporter-262-review/QaLifecycleTests.cs.txt` is a ready model) **and make the shutdown order-independent** (for example a `_disposed` flag or catching `ObjectDisposedException` around the cancel; the Developer's choice). Then the full unfiltered suite must be run and the Web project several times (the standing rule on tests that flake, `TESTING_STRATEGY.md` §11: fix the cause, not the symptom).
