## Tooling

`live_verify_capture_self_healing.py` (this directory) -- a script that owns daemon lifecycle for
each test (same start/stop discipline as `qa/endurance/*/tools/endurance_supervisor.py`: exact
given exe/config/port, no construction) and computes each row's predicate mechanically from the
daemon's own file log + `/api/v1/status` polls, never from a human read of the console.

**Self-caught script bug, fixed before trusting a result (worth recording per HK-018):** the first
L2 attempt (preserved at `../../artefacts/20260925_l1l4_capture_self_healing/L2-attempt1-scriptbug/`)
reported a false FAIL on L2-3. Cause: (a) the script's own regex looked for the word "adopt" in a
`[WRN]` line, but the real log wording is `"Capture device re-resolved: '<old>' -> '<new>'
(friendly name '<name>' unchanged)."` -- zero matches, not zero occurrences; (b) the capture-start
count was scanning the whole log directory, which also caught the unrelated precondition-probe
daemon's own start line from a separate process. Both are counting-scope defects in the
*verification script*, not the product. Fixed (match "re-resolved"; scope capture-start/warning
counts to only the log file the real post-edit daemon instance produced) and reran clean. The
product's actual behaviour (adoption within 30 s, correct config write-back, single warning,
single restart) was correct on the very first attempt -- only the check was wrong.

## Devices used

- **L1**: Voicemeeter Out B1 (VB-Audio Voicemeeter VAIO) -- the standing default routing
  (MEMORY.md: "Voicemeeter AUX Input -> B1"). Chosen because it was the live, connected chain at
  the time.
- **L2, L3**: same (B1) -- L2/L3 only need *a* valid, currently-available device to demonstrate
  adoption/rejection by friendly name; which physical device backs it is not load-bearing for
  those two rows.
- **L4**: switched to **Microphone (2- USB Audio CODEC )** -- the actual USB Audio Class endpoint
  the FT-991A itself exposes to Windows. This is deliberate, not incidental: Voicemeeter Out B1 is
  a virtual bus that stays enumerated by Windows and keeps delivering WASAPI buffers (of silence)
  regardless of what feeds it upstream -- confirmed empirically earlier in this session, when the
  radio was in an unrelated error state and B1's `dataFlowing` never left `true`. Pulling the
  FT-991A's cable only removes the *USB CODEC* device from Windows' own enumeration. L4 tests
  exactly that disappearance/reappearance, so it must run against the device that actually
  disappears. The handoff's own note ("WSJT-X reads the same physical device on a direct-CODEC
  arm") points the same way.

## Results

### L1 -- headless heartbeat and status (30 min)
`ws_accepted=0`, `heartbeat_count=360` (in range 330-370), `max_gap=5.0s` (<=7s), dataFlowing/
lastChunkAgeMs held after the first 10 s, `watchdogRestartCount=0` at the end. **PASS.**

Mid-run disclosure (HK-016/HK-022, does not affect the verdict): the FT-991A was independently in
an error state and was restored by the Captain during L1's early window, who then manually routed
its audio to match the daemon's already-armed B1 config. Every poll from L1's arm time onward
shows `dataFlowing=true`/`captureState=Capturing` continuously -- no gap registered, because L1's
own instrument cannot distinguish real signal from silence at the WASAPI-chunk level (HK-026); it
proves headless heartbeat/status, not "real signal was present throughout."

### L2 -- stale ID at startup is adopted
Precondition held (exactly one available device matching the configured friendly name). Adopted
within 30 s (`captureState=Capturing`, `dataFlowing=true`). `config.json` rewritten with the
correct `audioDeviceId`, friendly name unchanged. Exactly one adoption warning, exactly one capture
start after it. `ws_accepted=0`. **PASS** (after the script fix above; reran clean).

### L3 -- unresolvable device is loud, bounded, never guessed (300 s)
`captureState=DeviceUnavailable` with a populated `lastCaptureError` within 30 s.
`captureRestartCount` at t=300s was **8** (expected band 5-9, nominal 7). `config.json` unchanged;
zero adoption warnings. `ws_accepted=0`. **PASS.**

### L4 -- physical unplug and replug, no operator action
Captain physically unplugged the FT-991A's USB cable. Observed within the unplug window:
`captureState` -> `DeviceUnavailable`, `lastCaptureError` populated, device shows 0 matches in
`/api/v1/audio/devices` (`t_avail` reference point not yet available -- L4-0 satisfied, not VOID).
Captain replugged; `t_avail` (device reappears `available:true`) to `t_rec`
(`captureState=Capturing` and `dataFlowing=true`) = **~11.0 s**, well inside the <=70 s bound.
Post-recovery: `consecutiveCaptureFailures=0`, `lastCaptureError` still non-null (the last real
error, retained -- not cleared to null, matching the predicate). No GUID rotation observed (no
"re-resolved" warning in this window) -- L4-3 descriptive field, either outcome would have passed.
`ws_accepted=0` across the whole window. **PASS.**
